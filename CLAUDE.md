# Dirdigest Developer Guide

This document provides instructions for agents and developers working on the `dirdigest` codebase.

## 1. Environment & Build

This project uses **uv** for dependency management and **make** for task orchestration.

### Key Commands

- **Install Dependencies:**
  ```bash
  make install-deps
  # Or manually: uv sync --all-extras
  ```

- **Format Code:**
  ```bash
  make format
  # Uses: uv run ruff format .
  ```

- **Lint Code:**
  ```bash
  make lint
  # Uses: uv run ruff check --fix .
  ```

- **Type Check:**
  ```bash
  make mypy
  # Uses: uv run mypy --package dirdigest
  ```

- **Run All Tests:**
  ```bash
  make test
  # NOTE: This automatically handles fixture setup and cleanup.
  ```

- **Validate All (Format, Lint, Type, Test):**
  ```bash
  make validate
  ```

- **Install in dev mode (for CLI testing):**
  ```bash
  uv pip install -e .
  ```

## 2. Testing

The testing suite uses `pytest`. Tests are located in the `tests/` directory.

### Running a Single Test

**CRITICAL:** The tests rely on a fixture directory structure that is generated by a shell script. `make test` handles this automatically, but when running `pytest` directly (e.g., for a single test file or function), you **must** ensure the fixtures exist.

1.  **Generate Test Fixtures:**
    Run this script before running individual tests if the `tests/fixtures/test_dirs` directory is missing or stale.
    ```bash
    bash tests/scripts/setup_test_dirs.sh
    ```

2.  **Run Specific Test:**
    ```bash
    uv run pytest tests/test_cli_args.py
    # Or a specific case:
    uv run pytest tests/test_cli_args.py::test_cli_help_short_option
    ```

### Test Structure
- `tests/conftest.py`: Contains fixtures, including `temp_test_dir` which copies the generated mock directories to a temporary location for each test.
- `tests/scripts/setup_test_dirs.sh`: Generates the static fixture data in `tests/fixtures/test_dirs`.
- `tests/test_smart_patterns.py`: 90 unit tests for the pattern matching engine (anchoring, type discrimination, wildcards, specificity).
- `tests/test_specificity.py`: 32 tests for specificity-based conflict resolution (`resolve_pattern_conflicts`).
- `tests/test_traversal_filtering.py`: Integration tests for include/exclude filtering via the CLI.
- `tests/test_cli_args.py`: CLI argument parsing tests.

## 3. Architecture

### Core Modules

| Module | Purpose |
|--------|---------|
| `dirdigest/cli.py` | Click CLI entry point, `--dry-run` flag, pattern display |
| `dirdigest/core.py` | Directory traversal, `resolve_pattern_conflicts()`, digest tree building |
| `dirdigest/utils/patterns.py` | Smart pattern engine: `ParsedPattern`, `parse_pattern()`, `matches_path()`, specificity ranking |
| `dirdigest/formatter.py` | Output formatting (Markdown, JSON) via `BaseFormatter` hierarchy |
| `dirdigest/constants.py` | `DEFAULT_IGNORE_PATTERNS`, `TOOL_NAME`, `TOOL_VERSION` |
| `dirdigest/utils/` | Utility modules: logging, config, clipboard, system, tokens |

### Smart Pattern Rules (v1.0)

The `-i` (include) and `-x` (exclude) flags use a 7-rule pattern system. See `thoughts/shared/specs/2026-02-23-smart-pattern-rules.md` for the full spec.

**Key rules:**
1. **Anchoring:** `./` = exact from root, bare = suffix match at any depth, `**/` = explicit recursive
2. **Type discrimination:** trailing `/` = folders only, no slash = files only
3. **Wildcards:** POSIX standard (`*` = one level, `**` = recursive, `?` = one char)
4. **Specificity precedence:** When -i and -x conflict, most specific pattern wins (8-rank system). Ties = -x wins.
5. **Default ignores:** Always apply unless `--no-default-ignore`. -i does NOT override them.

**`--dry-run`/`--explain`:** Shows pattern resolution without producing a digest.

### Pattern Flow

```
CLI (cli.py)
  → parses -i/-x as strings
  → passes to core.process_directory_recursive()

Core (core.py)
  → parse_pattern() each string into ParsedPattern (once)
  → for each file/dir:
      1. Pre-checks: symlinks, hidden, default ignores
      2. resolve_pattern_conflicts() for user -i/-x specificity
  → yields included files

Patterns (utils/patterns.py)
  → ParsedPattern dataclass (anchored, is_folder, has_wildcards, segments, specificity)
  → matches_path(parsed, rel_path, is_dir) — core matching logic
  → _compute_specificity() — 8-level ranking (1=most specific)
```

## 4. Code Style & Conventions

### Language & Typing
- **Python Version:** Target Python >= 3.10.
- **Typing:** Strict static typing is required. Use `mypy` to verify.
  - Use `pathlib.Path` for all file system operations. Avoid `os.path` where possible.
  - Use `typing` module (e.g., `List`, `Tuple`, `Optional`) or standard collections in signatures.

### Imports
Imports are managed by `ruff` (configured to be compatible with `isort`).
- **Order:** Standard Library -> Third Party -> Local Application.
- **Local Imports:** Use absolute imports (e.g., `from dirdigest.core import ...`) rather than relative imports.

### Formatting
- **Line Length:** 120 characters.
- **Formatter:** `ruff format` (Black-compatible).
- **Quotes:** Double quotes `"` are preferred.

### Error Handling
- Use specific exception handling (avoid bare `except:`).
- Log errors using the project's logger (`dirdigest.utils.logger`), not `print`.
- For CLI errors, ensure `click` context is respected or handled gracefully to provide user-friendly exit codes.

### CLI & Output
- **Framework:** `click` is used for the CLI interface.
- **Output:** Use `rich` for console output.
  - Use `dirdigest.utils.logger.stdout_console` for printing to stdout.
  - Use `log.info`, `log.debug` etc. for logging.
- **Clipboard:** The tool supports clipboard operations via `pyperclip`. Ensure these are mocked in tests.

## 5. Workflow for Agents

1.  **Explore:** Start by listing files and reading `pyproject.toml` or `Makefile` if unsure about context.
2.  **Verify:** Before making changes, run `make validate` to ensure a clean state.
3.  **Edit:** Apply changes adhering to the style guide above.
4.  **Test:**
    - If modifying logic, run relevant existing tests.
    - If adding features, add new tests in `tests/`.
    - **Remember:** Run `bash tests/scripts/setup_test_dirs.sh` if you suspect fixtures are missing.
5.  **Finalize:** Run `make validate` again to ensure no regressions, linting errors, or type mismatches.

## 6. Specific Rules

- **No Relative Paths:** Always use absolute paths when using tool definitions (e.g., `read`, `write`).
- **Safety:** Do not modify the `tests/scripts/setup_test_dirs.sh` unless the test data requirements fundamentally change.
- **Logging:** Do not introduce `print()` statements for debugging in production code. Use the configured `logger`.
- **Pattern changes:** When modifying `utils/patterns.py`, run `tests/test_smart_patterns.py` (90 tests) first — it catches regressions fast.
